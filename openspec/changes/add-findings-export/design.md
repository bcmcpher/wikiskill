## Context

The pooled outputs (`leaderboard`, `leaderboard --by-version`, `report`) already compute everything a
finding needs. They read runs by id from a collection's evals or by path, so a directory holding only
`run.json` and `results.jsonl` loads like any run (`compare.load_run`). The version board labels
versions through `diff.versions`, which needs the collection's version store. Rates are formatted in
five places: `compare._fmt`, `leaderboard._fmt`, `gate._fmt`/`_rate_text`, `version_board._pct` and
`report._pct`. Delegation and activation detection is spread over:
- `runner/claude.py`: `_activation_name`, `_AGENT_TOOLS` and the delegation emit in `tool`
- `runner/opencode.py`: `_activation`, `_TASK_TOOLS` and `_tool_events`
- `score/judge.py`: `_AGENT_FIELDS` and `_AGENT_TOOLS`
- `hooks.py`: `AGENT_TOOLS`

The installed document skills build office files from JavaScript and read them with pandoc.
LibreOffice is installed; pandoc is not, and the user installs it.

## Goals / Non-Goals

**Goals:**
- A study's numbers can be regenerated from a clone, byte for byte.
- One study layout serves any suite, not just DSH.
- Office files import into Google Docs and Slides with editable text and tables.

**Non-Goals:**
- **Writing the prose.** The findings and their interpretation stay hand-written. Fragments carry
  the numbers only.
- **Native office charts.** Pandoc cannot write them, and PNG figures import everywhere.
- **Bundling transcripts.** They hold model output and paths that need no sharing. `run.json` and
  `results.jsonl` are already the files `docs/data.md` says to share.
- **A new statistics method.** The tables keep the existing intervals, directions and sign test.

## Decisions

**Study layout.** A study is a directory, and nothing in it depends on where it lives:
```
docs/pilots/dsh/
  findings.toml
  runs/<run_id>/{run.json,results.jsonl}    # bundled
  tables/<table>.md, <table>.slim.md        # fragments
  findings.csv
  figures/*.png
  report.md, slides.md                      # hand-written, include fragments
  reference.docx, reference.pptx            # optional templates
```
`findings.toml`:
```toml
[study]
name = "dsh-pilot"
collection = "dsh-archive"          # where `bundle` finds runs by id
models_file = "../../../pilots/models.toml"

[[runs]]
id = "01M46QWP6CTEM5DN807VS7GQMW"
role = "versions"
label = "v1"                        # a version label for runs of one component version

[[tables]]
name = "sweep"
kind = "leaderboard"                # leaderboard | version-board | report
roles = ["sweep", "versions"]

[[tables]]
name = "archive-doer-versions"
kind = "version-board"
roles = ["versions"]
component = "agent:archive/archive-doer"
baseline = "v1"
critical = "../../../pilots/archive-doer/critical.yaml"
```
Paths resolve from the study directory. Version labels come from the run entries, so a fresh clone
needs no version store. TOML matches the catalogue and the collection manifests.

**Bundle never overwrites.** A bundled run is a record, so a mismatch is a refusal and never a
refresh. Rerunning is the honest fix. Bundling skips runs already present by comparing content
hashes, so it is safe to rerun after each sweep run lands. `add-dsh-pilot`'s `sweep.sh` appends to
`findings.toml` via `wikiskill findings add <study> <run_id> --role sweep`, so the run log and the
study are one file. This is a small subcommand that refuses duplicates.

**Tables reuse the renderers.** `findings tables` calls the existing `leaderboard.pool`,
`version_board.pool` and `report.build_report` over the bundled runs. The full fragment is each
renderer's own output, its headings moved down two levels so it sits under the document's
sections. The slim fragment comes from the same object through a column
selection in `present.py`: model, family, condition, rate with interval, and lift or direction, at
most six columns, one table per file (a version board's per-model and overall tables are two), because
pandoc moves a second table on a slide to a slide of its own. Slides then never hand-trim a table. Both forms are written with a leading
`<!-- generated by wikiskill findings tables; do not edit -->` line, which `--check` uses to find
them.

**Long CSV, one schema for every kind.** The columns are:
- `table, kind, entrant, model, family, size_b, condition, version, task`
- `passed, total, rate, low, high, lift, direction`; `lift` is a version's rate less OFF's
- `outcomes` (JSON), `median_s, median_tokens_in, median_tokens_out, runs`

Pooled rows have an empty `task`. Long rather than wide, because a pivot is one step in any
spreadsheet and a wide sheet cannot be un-pivoted without knowing its layout. It uses the stdlib
`csv`.

**Figures as a PEP 723 script.** `bin/figures` declares `matplotlib` inline and runs with
`uv run --script`. uv caches the environment, the project lockfile stays honest, and figures are
optional: a study with no figures still builds. It draws two figures from the CSV:
- a forest plot of pass rates with intervals per model and condition, grouped by family as the
  catalogue orders them
- lift per version and model, with the baseline at zero

**Document build with pandoc.** `bin/build-docs <study>` is a Python stdlib script:
1. Refuse when `pandoc` is not on `PATH`.
2. Expand `<!-- include: tables/sweep.slim.md -->` lines into a temporary copy, refusing an include
   that is missing.
3. Run `pandoc report.md -o report.docx [--reference-doc reference.docx]`.
4. Run `pandoc slides.md -o slides.pptx --slide-level 2 [--reference-doc reference.pptx]`.
5. Write each output to a temporary name, renaming it into place only on success.

Considered alternatives:
- The docx/pptx skills' JavaScript generators would mean a hand-written program per document,
  with no markdown source to version.
- Marp writes slides as images, which Google Slides cannot edit.
- A pandoc Lua include filter would add a second language for a ten-line job.

`*.docx` and `*.pptx` under `docs/` are gitignored. Reference templates are binary but rarely
change, and are optional. The skills' `validate.py` and LibreOffice render serve as manual QA,
listed in tasks, not as a build dependency.

**Shared "how wikiskill works".** `docs/findings/how-wikiskill-works.md` and a slide-sized
`how-wikiskill-works.slides.md` explain:
- the loop
- OFF, ROUTED and INJECTED
- verifier-first scoring
- Wilson intervals and `direction`
- pooling
- the version board's panel, regressions and critical checks
- the gate
- judge panels and same-family marking

A study includes them like any fragment, so every report explains the method in the same words.

**`present.py`.** One formatter set:
- `rate(passed, total)` gives `9/10 (90%, 60-98%)`
- `count(passed, total)` gives `9/10`, where a cell has no room for an interval
- `pct(x, signed=False)`
- `MISSING = "—"`
- `table(header, rows)` builds markdown table rows
- `slim(...)` selects the slide-sized columns

`compare`, `leaderboard`, `version_board`, `gate` and `report` all use it. This is the one visible
change: `compare` drops the `CI` prefix, all outputs use `—`, and the interval is joined by a
hyphen. Test assertions on old strings are updated in one pass. The JSON outputs do not change.

**Report as a view over the pool.** `report.build_report` keeps its JSON shape. It gets the
following from `leaderboard.pool([run])` and its cells instead of `score.pass_rate` and its own
counters:
- each row's `pass_rate`
- `outcomes`, `tokens` and `wall_time_ms`
- the `pooled` section

Route metrics (`route@1`, confusion, routing loss) stay in `score`, which has no pooled equivalent.
Differences between the two paths come out as test failures and are settled in the pool's favour,
since the pool is what the specs define. Any row whose number changes is listed in the change's
notes.

**One call classifier.** `calls.py` (top level, stdlib only, so the hook imports it cheaply) holds:
- `SKILL_TOOLS`, `AGENT_TOOLS`, and `AGENT_FIELDS` (`subagent_type`, `subagentType`, `agent`,
  `name`)
- `target(tool, args) -> (kind, name) | None`, with `qualified` applied
- `delegation(tool, args, ok) -> {agent, description, prompt} | None`

The runners, `judge.delegations` and `hooks` import it. The harnesses' own quirks stay in their
runners: Claude Code's `plugin:name`, and OpenCode's state and status. The normalized event output
of both runners must not change; the existing normalize tests pin it.

## Risks / Trade-offs

- [The format change breaks people reading old outputs] → only the markdown changes, the JSON keys
  and values are untouched, and the change is stated in README.
- [The report refactor shifts a number] → the pool defines a pass and the old path is the outlier.
  Every changed row is named in tasks, not hidden.
- [A pandoc version renders tables or slides differently] → the build records `pandoc --version` in
  a `build.txt` beside the outputs. Versioned markdown is the record; office files are disposable.
- [Slide tables overflow] → slim fragments are limited to six columns. Long ones are split by family
  with `--rows` per slide, not shrunk.
- [Bundled runs grow the repo] → `results.jsonl` holds no transcripts, and about twenty models × 60
  units is a few MB. A study can be bundled and committed once per milestone.
- [The call classifier refactor changes what counts as a delegation] → the runners' normalize
  golden tests and the judge delegation tests must pass unchanged before anything else moves.

## Open Questions

None. A `report` table without a catalogue gives each judge's levels without family marks, as the
report itself does.
